# データモデル v2（校門配布 計画/実績 + 在籍 + 施策KPI）

智翔館NEP マーケティング・エージェントを「職員が使うWebアプリ＋エージェントAPI連携」へ拡張するための
データモデル。共有スプレッドシート（在籍/配布/母数/施策）の実態に合わせて再設計した。

> **個人情報は持たない（最重要）。** 共有シートには体験生・問い合わせ者の実名や担当者名が含まれるが、
> 取り込むのは**集計値のみ**。氏名・連絡先は一切DB／リポジトリに入れない。担当は役割名のみ（任意）。

## 組織構造

- **部門 (division)**: 中等部 / RED個別
- **地区 (area)** = 配布計画の単位。RED個別担当が地区（中等部分も統括）を計画。日宇のみ中等部担当。
- **拠点 (campus)** = 校舎・教室。各拠点はちょうど1つの部門に属し、1つの地区に属す。

## エンティティ

- `Division`（部門）… 中等部 / RED個別
- `Area`（地区）… 計画単位。`plannerRole`（RED個別担当 / 中等部担当）を持つ
- `Campus`（拠点）… `divisionId` / `areaId` を持つ
- `TargetSchool`（配布先学校）… 中/小、全校生徒数（母数, シート③）、ボトム配布目標
- `Enrollment`（在籍）… 拠点×月の在籍数（中等部=中1〜3、RED個別=全学年計）
- `Distribution`（配布）… 地区×配布先学校×日の **計画枚数 / 実績枚数**（Webアプリの主入力）
- `Response`（反応）… 拠点×チャネル×日のカウント（体験申込 / 問い合わせ / 入会）
- `Campaign`（施策）… 夏期動員などのフェーズ施策
- `KpiTarget`（KPI目標）… 施策のKPI（体験申込45 / 入会30 / 夏期動員150→230 など、シート④）

## スプレッドシートからの抽出方針（個人情報除外）

| シート | 抽出するもの | 落とすもの |
| --- | --- | --- |
| ①配布カレンダー | 地区×配布先学校×月の計画/実績枚数、ボトム | 担当者の個人名、細かな配布場所メモ |
| ②在籍 | 拠点×月の在籍数（中等部=中1〜3 / RED個別=計）。高等部は対象外 | 学年内訳・昨年比（任意で後日） |
| ③学校別生徒数 | 配布先学校の全校生徒数（母数） | （個人情報なし） |
| ④施策計画 | KPI目標値・施策名・フェーズ | **体験生/問い合わせ者の実名・紹介者名（全除外）** |

> 年度の確定: シートの「今年」は 2025年度 と推定（シート①に "2025" の記載）。
> 取込時に対象年を確定してから year_month を付ける。未確定値は「要検証」で扱う。

## 実装フェーズ

1. **モデル確定**（本ドキュメント + `webapp/prisma/schema.prisma` + 組織マスタseed）← 今ここ
2. **Webアプリ基盤**: Next.js + Prisma(SQLite) 立ち上げ、マイグレーション、マスタ投入
3. **データ入力UI**: 配布の計画/実績入力フォーム（地区×配布先学校×日）、在籍入力、一覧/ダッシュボード
4. **集計データ移行**: シート①②③から集計値を取り込み（個人情報除外、値は担当者が検証）
5. **エージェントAPI連携**: バックエンドが Claude API + 配布計算ロジックを呼ぶエンドポイント。
   職員がWeb UIから「配布計画 / 実績分析 / 提案」を実行できるようにする
6. **既存haifu-tool/slashコマンドの収束**: 同一DBを参照するよう移行

## 既存資産との関係

- 既存の Claude Code エージェント（CLAUDE.md / slashコマンド / haifu-tool / sql/分析）は当面そのまま維持。
- v2 は `webapp/` 配下を新しい中核に据え、最終的に同じ SQLite を共有して収束させる（フェーズ6）。
